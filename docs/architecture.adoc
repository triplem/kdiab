= kdiab Platform Architecture
:toc: left
:icons: font

== Overview

kdiab is a Type 1 Diabetes management platform structured as a monorepo containing four independent
services that share infrastructure, configuration, and CI/CD tooling.

== Technology Stack

All four services share the same stack:

[cols="1,3"]
|===
| Layer | Technology

| Language        | Kotlin
| Framework       | Ktor (server) / React 19 + TypeScript + Vite (frontend)
| Build           | Gradle Kotlin DSL / npm
| API Contract    | OpenAPI 3.0 (single source of truth for code generation)
| Persistence     | PostgreSQL + Exposed ORM + HikariCP + Liquibase
| Authentication  | Keycloak (JWT / JWKS)
| Containerisation| Docker / Podman with Docker Compose
| Code Quality    | Detekt (linting), Kover (80% coverage), CycloneDX (SBOM)
| Releases        | Conventional Commits + Semantic Release
| CI/CD           | GitHub Actions (path-filtered per service)
|===

== Architectural Pattern

All services follow *Hexagonal Architecture* (Ports and Adapters):

[source]
----
adapters/inbound/web/        HTTP layer: route handlers + mapper (API ↔ domain)
application/service/         Business logic (orchestrates domain + ports)
domain/model/                Pure domain model (no framework dependencies)
domain/repository/           Port interfaces (not in kdiab-bff — no DB)
domain/exception/            DomainExceptions mapped to HTTP status by StatusPages
infrastructure/persistence/  Exposed ORM + PostgreSQL adapter
adapters/outbound/http/      Ktor HTTP clients (kdiab-bff only — calls upstream services)
plugins/                     Ktor plugin config (Security, StatusPages, Logging, CallId)
----

== API-First Design

`api/openapi.yaml` is the contract between frontend and backend in every service.
Code is generated from it on both sides:

* *Backend*: `openApiGenerate` Gradle task → Ktor server stubs + model classes
  into `backend/build/generated/api/`. Runs automatically before `compileKotlin`.
* *Frontend*: `npm run api:generate` → TypeScript/Axios client into
  `frontend/src/api/generated/`. Runs automatically before `npm run build`.

When changing the API, update `api/openapi.yaml` first, then regenerate on both sides.

== Authentication & Authorisation

JWT-based via Keycloak. `UserPrincipal` extracted from the JWT carries:

* `userId: Uuid` (from `sub` claim)
* `roles: Set<Role>` — `PATIENT`, `DOCTOR`, `ADMIN`
* `allowedPatients: Set<Uuid>` — for doctors

Access control rule: `UserPrincipal.canAccess(targetUserId)` returns true for self, any admin,
or a doctor whose `allowedPatients` contains `targetUserId`.

=== kdiab-bff JWT Forwarding

The BFF receives a user JWT and forwards it unchanged to all upstream services. For this to work
the Keycloak client must have audience mappers for all four audiences (`bff`, `measure`, `profile`,
`treatment`). The root `config/keycloak-realm.json` configures the `kdiab-bff-frontend` client
with all four audience mappers.

== CI/CD Pipeline

Each service has two CI workflows (backend and frontend) triggered by path filters:

[source,yaml]
----
on:
  push:
    paths:
      - 'kdiab-measures/backend/**'
      - 'kdiab-measures/api/openapi.yaml'
----

Workflow names follow the convention `kdiab-<service> / Backend CI` to ensure uniqueness, since
release workflows reference CI workflows by name via `workflow_run` triggers.

See link:adr/ADR-001-monorepo-consolidation.html[ADR-001] for full details on the CI/CD consolidation.

== Seed Data

The full platform stack seeds 30 days of realistic data for test users `sarah` and `mike`:

* *kdiab-measures*: 8 640 CGM readings/user (5-min intervals, sine-wave glucose curve) + 120 BGM readings/user
* *kdiab-treatments*: 3 bolus+carbs pairs/day/user + occasional corrections for sarah
* *kdiab-profiles*: one ARCHIVED + one ACTIVE profile for sarah, one ACTIVE profile for mike
