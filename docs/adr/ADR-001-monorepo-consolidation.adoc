= ADR-001: Monorepo Consolidation
:toc: left
:icons: font

* *Status*: Accepted
* *Date*: 2026-05-02
* *Deciders*: triplem

== Context

The four kdiab services (`kdiab-measures`, `kdiab-profiles`, `kdiab-treatments`, `kdiab-analyze`) share a root
directory under a single parent git repository, but were developed as partially independent repositories:

* `kdiab-profiles` and `kdiab-treatments` each had their own `.git` directory with independent commit history.
* All four service directories were *untracked* in the root repository.
* Each service had its own `.github/workflows/` directory containing CI/CD pipelines that only functioned
  when that service directory was the git root — making them effectively dead code in the monorepo context.
* `kdiab-treatments` had no release pipeline at all; `kdiab-analyze` had no CI pipelines.

This fragmented setup caused several problems:

* Running `git status` at the root showed all service directories as untracked.
* Per-service GitHub Actions workflows were unreachable from the root repository.
* Dependabot, SonarCloud, and semantic-release were configured per-service rather than centrally.
* Two separate nested git histories existed alongside the root history with no relationship between them.

== Decision

Consolidate all services into a single true monorepo under the existing root `.git`:

1. *Delete nested `.git` directories* (`kdiab-profiles/.git`, `kdiab-treatments/.git`).
   Pre-monorepo history in these repos is a one-time loss accepted as the cost of consolidation.
2. *Track all service directories* in the root repository via `git add`.
3. *Consolidate all CI/CD* into a single root `.github/` directory, with per-service workflow files
   that use path filters (`kdiab-<service>/`) to trigger only on relevant changes.
4. *Add missing pipelines*: release workflows for `kdiab-treatments` and `kdiab-analyze`, which were
   previously absent.
5. *Unify Dependabot* into a single root `.github/dependabot.yml` covering all services.
6. *Unify GitHub Pages* documentation into a single deployment covering all services.
7. *Expand root `.gitignore`* to cover all artifact types (Gradle, Node.js, IntelliJ, etc.).

The per-service directory structure (`kdiab-<service>/backend/`, `kdiab-<service>/frontend/`) is
*preserved unchanged*. Each service continues to have its own Gradle build, `docker-compose.yml`,
and OpenAPI spec.

== Workflow Naming Convention

GitHub Actions workflow names must be globally unique within a repository because `workflow_run`
triggers reference them by name. Each workflow is named `kdiab-<service> / <Type>`:

[cols="2,3"]
|===
| File | Name

| `ci-measures-backend.yml`   | `kdiab-measures / Backend CI`
| `ci-measures-frontend.yml`  | `kdiab-measures / Frontend CI`
| `ci-profiles-backend.yml`   | `kdiab-profiles / Backend CI`
| `ci-profiles-frontend.yml`  | `kdiab-profiles / Frontend CI`
| `ci-treatments-backend.yml` | `kdiab-treatments / Backend CI`
| `ci-treatments-frontend.yml`| `kdiab-treatments / Frontend CI`
| `ci-bff-backend.yml`        | `kdiab-analyze / Backend CI`
| `ci-bff-frontend.yml`       | `kdiab-analyze / Frontend CI`
| `release-measures.yml`      | `kdiab-measures / Release`
| `release-profiles.yml`      | `kdiab-profiles / Release`
| `release-treatments.yml`    | `kdiab-treatments / Release`
| `release-bff.yml`           | `kdiab-analyze / Release`
| `docs-pages.yml`            | `Deploy Documentation`
|===

== Path Filter Conventions

All workflow path filters are prefixed with the service directory:

[source,yaml]
----
# Before (per-service repo)
paths:
  - 'backend/**'
  - 'api/openapi.yaml'

# After (monorepo root)
paths:
  - 'kdiab-measures/backend/**'
  - 'kdiab-measures/api/openapi.yaml'
----

All `working-directory` defaults and `cd` prefixes in run steps are similarly updated.

== GitHub Pages

Both `kdiab-measures` and `kdiab-profiles` previously had independent Pages deployments. A GitHub
repository has a single `github-pages` environment, so a single `docs-pages.yml` workflow now builds
AsciiDoc documentation for all three backend services and deploys them under a unified site:

* `/measures/` → `kdiab-measures/build/docs/asciidoc`
* `/profiles/` → `kdiab-profiles/build/docs/asciidoc`
* `/treatments/` → `kdiab-treatments/build/docs/asciidoc`
* `/` → root `docs/` (architecture, how-to-run, ADRs)

== Consequences

=== Positive

* Single `git clone` gives full project history and all services.
* Cross-service changes (e.g. shared config, root `docker-compose.yml`) are atomic commits.
* CI pipelines are active and path-filtered — only relevant services build on change.
* Release pipelines exist for all four services.
* Dependabot keeps all services updated from one configuration.

=== Negative

* Pre-monorepo git history of `kdiab-profiles` (5 commits) and `kdiab-treatments` (1 commit) is lost
  from the nested repos. The root repo history begins from this consolidation commit.
* The root repository becomes larger; shallow clones (`--depth=1`) recommended for CI to keep
  checkout times short.

=== Neutral

* Each service's internal build system (`./gradlew`, `npm`) is unchanged.
* Per-service `docker-compose.yml` files remain for standalone development.
* The root `build.sh` orchestration script handles cross-service builds.

== Alternatives Considered

=== Git Submodules

Keep each service as an independent repo and link them via git submodules from the root. *Rejected*:
submodules add significant workflow complexity (recursive checkout, independent commit cycles,
submodule pointer management) for no practical benefit in this project.

=== Turborepo / Nx

Use a JS-native monorepo tool. *Rejected*: the backend services are Kotlin/Gradle, not JavaScript.
These tools add orchestration overhead appropriate for pure JS workspaces but provide no value here
where `build.sh` already handles orchestration.

=== Keep services as independent repos

Continue with separate repositories and a root directory that is purely an orchestration layer.
*Rejected*: the root `.git` already exists and the intent is clearly a monorepo; maintaining split
repos creates ongoing friction (separate PRs for cross-service changes, dead workflow files,
Dependabot on multiple repos).
