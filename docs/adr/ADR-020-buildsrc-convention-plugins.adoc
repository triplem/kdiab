= ADR-020: build-logic Included Build for Convention Plugins
:toc: left
:icons: font

* *Status*: Accepted
* *Date*: 2026-06-02
* *Deciders*: triplem

== Context

Every kdiab backend service had its own `build.gradle.kts` of 200–380 lines. Approximately 80%
of that content was identical across all 9 services: JVM toolchain configuration, Detekt, Kover,
test suite registration, Asciidoctor, and OpenAPI code generation defaults. Changing any shared
convention — for example, bumping the minimum Kover coverage threshold or adding a new Detekt
rule — required manual edits to 8–9 separate files.

Gradle provides two mechanisms for sharing build logic across a composite build:

* **`buildSrc/`** — a special magic directory Gradle auto-discovers and compiles before any build
  runs. Precompiled script plugins placed there become available to all subproject build scripts.
* **Explicit `build-logic/` included build** — a normal Gradle project included via
  `pluginManagement { includeBuild("build-logic") }` in root `settings.gradle.kts`. Plugins are
  consumed by name; no magic auto-discovery.

Both support precompiled script plugins (`.gradle.kts` files compiled to Gradle plugins).

== Decision

Use an explicit `build-logic/` included build (not `buildSrc/`) with a three-plugin hierarchy:

[cols="1,3"]
|===
| Plugin | Applies to

| `kdiab.kotlin-base`
| All Kotlin builds — JVM toolchain (21), Kotlin serialization, Detekt, repositories,
  kotlin-test-junit5, shared `jvmArgs` for tests

| `kdiab.ktor-service`
| All Ktor HTTP services — extends `kdiab.kotlin-base`, adds Ktor server deps, logging,
  test suites (integrationTest, e2eTest), Kover, Asciidoctor, OpenAPI server codegen defaults,
  `apiSpec` outgoing configuration (exposes `api/openapi.yaml` as a resolvable Gradle artifact)

| `kdiab.ktor-db-service`
| DB-backed services — extends `kdiab.ktor-service`, adds Exposed + database bundle,
  H2 on integrationTestImplementation
|===

`build-logic/settings.gradle.kts` explicitly re-declares the root `gradle/libs.versions.toml`
version catalog (not auto-inherited in an included build).

`build-logic/build.gradle.kts` pins each plugin dependency version against the same catalog
using `findVersion(...).get().requiredVersion`, so plugin versions stay in sync with library
versions from a single source of truth.

== Rationale for build-logic over buildSrc

Two concrete advantages drove this choice:

. **Configuration cache invalidation scope.** Any file change under `buildSrc/` invalidates the
  Gradle configuration cache for the entire composite build. An included build is isolated: only
  its own outputs are tracked. On a 9-service monorepo with a warm cache (202 tasks), this
  difference is measurable on every developer iteration.

. **Buildscript classpath isolation.** `buildSrc/` puts all its transitive compile dependencies
  (8 plugin JARs) onto the buildscript classpath of every service project. An included build's
  classpath is scoped to the included build alone, reducing the risk of classpath conflicts when
  adding heavyweight plugins.

The Gradle documentation now recommends included builds over `buildSrc` for new projects for
exactly these reasons.

== Consequences

=== Positive

* Shared conventions change in one place — one commit to `build-logic/` updates all 9 services.
* Service build files shrank to 20–80 lines containing only service-specific overrides
  (down from 200–380 lines).
* Configuration cache benefits on repeated local builds.
* `gradle/openapi-defaults.properties` deleted; defaults now live in `kdiab.ktor-service`.

=== Negative

* `build-logic/` has no version — changes to plugins apply to all services simultaneously with
  no gradual rollout path. A breaking change to the convention plugin breaks every service build
  at once.
* Developers must understand the two-level build model: `build-logic` compiles as a separate
  Gradle build whose outputs are consumed as plugins by the service builds.
* The version-catalog type-safe accessor (`libs.xxx`) is **not** available inside precompiled
  script plugins — the generated accessor class only exists in consuming projects. Plugin scripts
  must use `project.extensions.getByType<VersionCatalogsExtension>().named("libs")` directly.

=== Neutral

* `maven-publish` and `publishing {}` stay in `kdiab-common/build.gradle.kts` — they are
  specific to the shared library distribution concern and must not be centralised.
* Each service still defines its own `kover { reports { verify { rule { bound { minValue = 80 } } } } }`
  block with service-specific package exclusions. A global rule in the convention plugin would
  fail on adapter/plugin packages not covered by unit tests.

== Alternatives Considered

=== `buildSrc/` magic directory

Auto-included by Gradle before the build runs; no explicit `includeBuild` needed.
*Not chosen*: invalidates the configuration cache on every plugin change (worse for large builds);
leaks plugin JARs onto all subproject buildscript classpaths.

=== Script sharing via `apply from:`

Import a shared `.gradle.kts` file from a URL or local path in each service build.
*Rejected*: no type safety, no IDE support, executes at configuration time with no compilation
step. Harder to maintain than precompiled plugins.

=== Root `subprojects {}` block

Move all services to Gradle subprojects of a root build instead of a composite build.
*Rejected*: would require restructuring the monorepo and losing independent service builds.
Each service can already be built in isolation — this property must be preserved.
