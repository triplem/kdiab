= ADR-021: OpenAPI Spec Artifact Distribution in Gradle Composite Builds
:toc: left
:icons: font

* *Status*: Accepted
* *Date*: 2026-06-02
* *Deciders*: triplem

== Context

Three kdiab services consume upstream OpenAPI specs to generate typed Kotlin clients:

[cols="1,3"]
|===
| Consumer | Upstream specs consumed

| kdiab-analyze
| kdiab-measures, kdiab-treatments, kdiab-profiles

| kdiab-nightscout
| kdiab-measures, kdiab-treatments, kdiab-carbs, kdiab-profiles, kdiab-users

| kdiab-calc
| kdiab-profiles
|===

Before this ADR, each consumer referenced upstream specs with a hard-coded relative path:

[source,kotlin]
----
inputSpec.set(layout.projectDirectory.file("../kdiab-measures/api/openapi.yaml").asFile.absolutePath)
----

This approach has three problems:

. *Invisible to Gradle's dependency graph* — Gradle does not track the file as an input, so
  changes to the upstream spec do not invalidate the consumer's `GenerateTask`. Developers must
  run clean builds manually.
. *Fragile to directory changes* — the path breaks silently if the monorepo layout is restructured.
. *Does not work for standalone service builds* — the CI runs each service independently
  (`cd kdiab-analyze && ./gradlew :check`). Per-service `settings.gradle.kts` files do not
  include the upstream services, so relative paths resolve against the wrong base.

ADR-005 established that `api/openapi.yaml` in each service directory is the single source of truth.
This ADR decides how that file is made available to downstream services as a proper Gradle artifact.

== Decision

Use Gradle's outgoing variant mechanism combined with composite-build `dependencySubstitution`
to expose each service's `api/openapi.yaml` as a resolvable artifact under a typed coordinate.

=== 1. Outgoing configuration in `kdiab.ktor-service`

The convention plugin (`build-logic/src/main/kotlin/kdiab.ktor-service.gradle.kts`) registers
an outgoing `apiSpec` configuration on every Ktor service:

[source,kotlin]
----
val apiSpec by configurations.creating {
    isCanBeConsumed = true
    isCanBeResolved = false
    attributes {
        attribute(Category.CATEGORY_ATTRIBUTE, objects.named(Category::class, "openapi-spec"))
    }
}
artifacts {
    add("apiSpec", layout.projectDirectory.file("api/openapi.yaml"))
}
----

The `org.gradle.category = openapi-spec` attribute uniquely distinguishes this variant from the
default JAR variant. No `capability` declaration is needed — the attribute alone resolves
ambiguity when the consumer declares a matching attribute on its resolvable configuration.

=== 2. Dependency substitution in `settings.gradle.kts`

Both the root `settings.gradle.kts` and each consumer service's own `settings.gradle.kts` include
the upstream service builds and declare substitution rules:

[source,kotlin]
----
// root settings.gradle.kts  (root path: "kdiab-measures"; per-service path: "../kdiab-measures")
includeBuild("../kdiab-measures") {
    dependencySubstitution {
        substitute(module("org.javafreedom.kdiab:kdiab-measures")).using(project(":"))
        substitute(module("org.javafreedom.kdiab:kdiab-measures-spec")).using(project(":"))
    }
}
----

Two substitution rules are declared per service: one for the JAR coordinate (pre-existing) and
one for the spec coordinate (added by this ADR). Both map to the same project root (`":"`).
Gradle selects the correct variant based on the consumer configuration's `Category` attribute.

The spec coordinate convention is `org.javafreedom.kdiab:kdiab-{service}-spec`.
No version is required in composite builds — substitution matches regardless of the version component.

Per-service `settings.gradle.kts` files for consumer services repeat the relevant `includeBuild`
blocks so that standalone builds (`cd kdiab-analyze && ./gradlew :check`) also resolve spec
artifacts from local sources without a `publishToMavenLocal` pre-step.

=== 3. Consumer pattern

A downstream service declares a dedicated resolvable configuration per upstream spec:

[source,kotlin]
----
import org.gradle.api.attributes.Category
import org.openapitools.generator.gradle.plugin.tasks.GenerateTask

val measuresSpec by configurations.creating {
    isCanBeConsumed = false
    isCanBeResolved = true
    attributes {
        attribute(Category.CATEGORY_ATTRIBUTE, objects.named(Category::class, "openapi-spec"))
    }
}

dependencies {
    measuresSpec("org.javafreedom.kdiab:kdiab-measures-spec")
}

val generateMeasuresModels by tasks.registering(GenerateTask::class) {
    generatorName.set("kotlin")
    inputSpec.set(provider { measuresSpec.singleFile.absolutePath })   // <1>
    outputDir.set("${layout.buildDirectory.get()}/generated/upstream-measures")
    // further generator options ...
}

tasks.compileKotlin {
    dependsOn(generateMeasuresModels)
}

kotlin {
    sourceSets {
        main {
            kotlin.srcDir(layout.buildDirectory.dir("generated/upstream-measures/src/main/kotlin"))
        }
    }
}
----
<1> The `provider { }` wrapper is required. Calling `measuresSpec.singleFile.absolutePath`
    eagerly at configuration time would fail because the configuration has not yet been resolved.

== Consequences

=== Positive

* Upstream spec changes are tracked by Gradle's input hashing — the consumer's `GenerateTask`
  is invalidated automatically when `api/openapi.yaml` changes upstream.
* No hardcoded filesystem paths remain in consumer build scripts.
* Every service that applies `kdiab.ktor-service` is automatically a spec provider with zero
  extra per-service configuration.
* Standalone per-service CI builds resolve specs from local included builds without any
  `publishToMavenLocal` pre-step.
* Adding a new consumer requires only a configuration declaration, a `GenerateTask` block, and
  an `includeBuild` entry in `settings.gradle.kts`; no changes are needed in the upstream service.

=== Negative

* The `dependencySubstitution` blocks must appear in both the root `settings.gradle.kts` and
  each consumer service's own `settings.gradle.kts`. A new consumer that omits the latter will
  fail its standalone CI build with:
  `Could not find org.javafreedom.kdiab:kdiab-*-spec`.
* Generating models from multiple upstream specs (kdiab-nightscout uses 5) adds multiple
  `includeBuild` blocks and `GenerateTask` registrations to the service's build files.
* Generated packages must be excluded from Kover coverage to prevent false failures on code
  that cannot be meaningfully unit-tested.

=== Neutral

* Client code is generated inside the downstream service; upstream services remain unaware of
  their consumers (no coupling inversion).
* A single `dependencySubstitution` rule per project (mapping both `kdiab-measures` and
  `kdiab-measures-spec` to `project(":")`) works because Gradle's variant-aware resolution
  selects the correct artifact based on the consumer's attributes — not the coordinate suffix.

== Alternatives Considered

=== Hard-coded relative paths (status quo)

Keep `../kdiab-*/api/openapi.yaml` references.
*Rejected*: invisible to Gradle's input tracking (no automatic task invalidation); breaks on
directory restructure; and fails for standalone CI builds that run from inside the service directory.

=== `publishToMavenLocal` pre-step

Each upstream service publishes its spec to the local Maven repository before consumers build.
*Rejected*: requires a manual or CI pre-step; breaks clean build semantics; the published
artifact may lag behind uncommitted local spec changes.

=== Direct `files(...)` dependency

Reference the file directly: `dependencies { measuresSpec(files("../kdiab-measures/api/openapi.yaml")) }`.
*Rejected*: preserves the fragile relative path and still does not integrate with Gradle's
versioned artifact dependency graph.

=== Publish client JARs from upstream services

Each upstream service generates and publishes a typed Kotlin HTTP client JAR.
*Rejected*: forces upstream services to know about client generation concerns; requires a
publish step on every upstream spec change; couples upstream and downstream versioning.

=== Separate spec repository / Git submodules

Store all `api/openapi.yaml` files in a shared repository.
*Rejected*: out of scope for a monorepo; moves spec ownership away from the service that owns
the API contract; adds submodule management overhead.
