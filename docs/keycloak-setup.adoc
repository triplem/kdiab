= Keycloak Setup Guide
:toc: left
:icons: font

This document explains the Keycloak realm configuration used by kdiab and how to recreate or modify it.

== Overview

kdiab uses a single Keycloak realm named `kdiab`. The realm configuration lives in `config/keycloak-realm.json` and is imported automatically when the root `docker compose up` starts the Keycloak container.

Each of the four frontends has its own Keycloak client (public client, PKCE S256). All four clients share the same realm, roles, and test users.

== Realm Configuration

=== Realm settings

[cols="1,2"]
|===
| Setting | Value

| Realm name
| `kdiab`

| SSL required
| External requests only (`external`)

| Registration
| Disabled

| Login theme
| `kdiab` (custom dark theme; served from the Keycloak container)

| Locales
| English (default), German
|===

=== Roles

Three realm roles are defined:

[cols="1,3"]
|===
| Role | Description

| `PATIENT`
| End user who owns health data. Can read and write their own measurements, profiles, and treatments.

| `DOCTOR`
| Clinician with read access to a specific set of patients. Allowed patient IDs are listed in the `allowed_patients` JWT claim.

| `ADMIN`
| Platform administrator with unrestricted access to all user data.
|===

=== Test Users

All test accounts use password `password`.

User UUIDs are fixed (deterministic) in the realm export so that the seed SQL can reference them directly.

== Clients

=== Client configuration (all four clients)

Each frontend has a separate client with identical security settings:

[cols="1,2"]
|===
| Setting | Value

| Client type
| Public (no client secret)

| PKCE
| S256 (`pkce.code.challenge.method=S256`)

| Redirect URIs
| `http://localhost:*`

| Web origins
| `http://localhost:3000` through `http://localhost:3004` (explicit list, no wildcard)
|===

=== Client list

[cols="1,1,1"]
|===
| Client ID | Frontend service | Audience(s) in token

| `kdiab-measures-frontend`
| kdiab-measures (port 3004)
| `measure`

| `kdiab-profiles-frontend`
| kdiab-profiles (port 3001)
| `profile`

| `kdiab-treatments-frontend`
| kdiab-treatments (port 3002)
| `treatment`

| `kdiab-analyze-frontend`
| kdiab-analyze (port 3003)
| `analyze`, `measure`, `profile`, `treatment`
|===

The analyze frontend client has **four** audience mappers because the BFF forwards the user's token unchanged to all three upstream services. The token must be accepted by all four backends simultaneously.

== Protocol Mappers

Each client has the following protocol mappers configured:

=== Roles mapper

Adds the user's realm roles as a `roles` claim (string array) to the access token.

[source,json]
----
{
  "name": "roles",
  "protocolMapper": "oidc-usermodel-realm-role-mapper",
  "config": {
    "claim.name": "roles",
    "multivalued": "true",
    "access.token.claim": "true"
  }
}
----

NOTE: The standard Keycloak `realm_access.roles` claim is not reliably present in all OIDC flows. The frontend reads roles from the flat `roles` array instead.

=== Audience mapper

Adds the service audience to the `aud` claim so the backend's JWT validator can verify the token is intended for it.

=== User attribute mappers

`glucose_unit` and `weight_unit` are custom user attributes mapped to same-named claims in both access token and ID token. The frontend reads these from the ID token to display values in the user's preferred unit. The backend BFF reads them from the access token to perform unit conversion.

`allowed_patients` is a multi-valued user attribute mapped to a string array claim in the access token only. The backend extracts this into `UserPrincipal.allowedPatients` to enforce doctor-patient access control.

== How JWT Forwarding Works

The kdiab-analyze BFF receives the user's bearer token and forwards it unchanged to all upstream services:

[source]
----
Browser  →  kdiab-analyze-frontend  →  kdiab-analyze-backend
                                              │
                        ┌─────────────────────┼──────────────────────┐
                        ▼                     ▼                      ▼
               kdiab-measures       kdiab-profiles        kdiab-treatments
----

Because the token carries `aud: ["analyze", "measure", "profile", "treatment"]`, each upstream backend accepts it without requiring a separate login or token exchange.

== Recreating the Realm from Scratch

The realm JSON is imported automatically by the Keycloak container on first startup:

[source,yaml]
----
keycloak:
  command: start-dev --import-realm
  volumes:
    - ./config/keycloak-realm.json:/opt/keycloak/data/import/kdiab-realm.json
----

To recreate after a change:

. Edit `config/keycloak-realm.json` with the desired changes.
. Tear down the stack including Keycloak's volume: `docker compose down -v`
. Start again: `docker compose up --build`

Alternatively, make changes in the Keycloak Admin UI (http://localhost:8081) and export the realm:

[source,bash]
----
docker exec -it kdiab-keycloak \
  /opt/keycloak/bin/kc.sh export \
  --realm kdiab \
  --file /tmp/kdiab-realm.json
docker cp kdiab-keycloak:/tmp/kdiab-realm.json config/keycloak-realm.json
----

== Production Considerations

* Replace the test user passwords and remove test accounts.
* Set `sslRequired` to `all` (requires HTTPS for all connections).
* Configure a production-grade Keycloak database (not the embedded H2).
* Store the Keycloak admin password in a secret manager, not a `.env` file.
* Review and tighten Web Origins — replace the localhost list with your production domain.

See link:deployment.html[Deployment Guide] for full production hardening guidance.
