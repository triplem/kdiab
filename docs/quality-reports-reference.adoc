= Quality Reports — Reference Guide
:toc: left
:icons: font

This reference covers the report URL structure on GitHub Pages, the pipeline that generates reports, and how to extend the pipeline for a new service.

== Published URL Structure

Reports are generated by `docs-pages.yml` on every push to `main` and published to GitHub Pages.
The site root is `https://triplem.github.io/kdiab/`.

== Adding a New Service

When a new kdiab backend service is created, follow this checklist to add it to the report pipeline.

=== 1. `docs-pages.yml` — build-service matrix

Add an entry to the `build-service` matrix in `.github/workflows/docs-pages.yml`:

[source,yaml]
----
- service: kdiab-<name>
  page: <name>
----

No other changes to `build-service` are needed — the Gradle commands, Redocly, Docker build, Trivy, and staging steps apply to all matrix entries.

=== 2. `docs-pages.yml` — assemble job

Add a download step to the `assemble` job:

[source,yaml]
----
      - name: Download <name> docs
        if: always()
        continue-on-error: true
        uses: actions/download-artifact@v4
        with:
          name: docs-<name>
          path: pages/<name>/
----

Add `build-service` to the `needs:` list if it's not already there (it is, so no change needed).

=== 3. Root docs index

Add a row for the new service to the Quality Reports table in `docs/index.adoc`.

=== 4. Service docs index

Add a `== Quality Reports` section to `<service>/docs/index.adoc` following the pattern in the existing service indexes. Include only the test types that apply (omit integration/e2e if those suites don't exist).

=== 5. Detekt baseline

Ensure `<service>/config/detekt/baseline.xml` exists — the `kdiab.kotlin-base` convention plugin requires it.

== Pipeline Design Notes

=== Kover output path

Kover HTML reports are generated by `./gradlew koverHtmlReport` and land in `build/reports/kover/html/` (not `build/reports/kover/htmlReport/` or `build/reports/kover/`). The staging step in `build-service` copies this directory to `staging/<page>/reports/coverage/`.

=== Trivy HTML template

`aquasecurity/trivy-action@v0.36.0` bundles `@/contrib/html.tpl` alongside the `@/contrib/gitlab.tpl` and `@/contrib/junit.tpl` templates. The `@` prefix is a Trivy convention for built-in templates. The template produces an HTML page with a vulnerability table grouped by severity.

=== Dual-scan pattern

The CI security gate (`backend-ci-reusable.yml`) runs Trivy with `exit-code: 1` on CRITICAL/HIGH and produces SARIF output for the GitHub Security tab. The docs pipeline (`docs-pages.yml`) runs a second, non-blocking Trivy scan (`exit-code: 0`) and produces HTML for the Pages site. These are independent: the CI scan gates merges; the docs scan provides persistent visibility. See link:adr/ADR-022-report-publishing-strategy.html[ADR-022] for the full rationale.

=== Partial failures

All report-generating steps use `continue-on-error: true`. If a Gradle build fails (e.g. tests red), the staging step (`if: always()`) and upload step (`if: always()`) still run, uploading whatever reports were generated before the failure. The assemble job uses `if: always()` + `continue-on-error: true` on all download steps so the deploy succeeds even when one service artifact is missing.
