= kdiab-treatments Operations Guide
:author: kdiab team
:toc: left
:toclevels: 3

== Overview

`kdiab-treatments` is the treatment event store for the kdiab platform. It persists bolus, basal, carb entries, correction boluses, combo boluses, temp basals, exercise, notes, BG checks, pump events, site changes, sensor inserts, and insulin changes. It runs on port 8083.

== Configuration

All configuration is provided via environment variables (override the defaults in `application.conf`).

=== Required Variables

|===
| Variable | Description | Example

| `JWKS_URL` | Keycloak JWKS endpoint for JWT verification | `http://keycloak:8080/realms/kdiab/protocol/openid-connect/certs`
| `JWT_DOMAIN` | JWT issuer domain | `http://localhost:8081/realms/kdiab`
| `JWT_AUDIENCE` | Expected `aud` claim in JWTs | `treatment`
| `JDBC_URL` | PostgreSQL JDBC URL | `jdbc:postgresql://postgres:5432/kdiab-treatments`
| `DB_USER` | PostgreSQL username | `kdiab_treatments`
| `DB_PASSWORD` | PostgreSQL password | _(from secrets manager)_
|===

=== Optional Variables

|===
| Variable | Default | Description

| `PORT` | `8080` | HTTP listen port (external port 8083 mapped by Docker)
| `JWT_REALM` | `kdiab-treatments` | Keycloak realm name (cosmetic; not validated)
| `CORS_ALLOWED_ORIGINS` | `http://localhost:3000` | Comma-separated allowed CORS origins
| `DB_POOL_SIZE` | `10` | HikariCP maximum connection pool size
| `DB_RUN_MIGRATIONS` | `false` | Run Liquibase migrations on startup. Set `true` only in test/local envs; production uses the `liquibase-treatments` container.
| `APP_INIT_DATABASE` | `true` | Connect to the database on startup. Set `false` for test environments without a real DB.
| `LOGGING_SUPPRESS_HEALTH_CHECKS` | `true` | Suppress health check paths from access logs
| `JSON_PRETTY_PRINT` | `false` | Pretty-print JSON responses (development only)
| `SWAGGER_ENABLED` | `false` | Serve Swagger UI at `/swagger`
| `OTEL_SERVICE_NAME` | — | OpenTelemetry service name (set to `kdiab-treatments`)
| `OTEL_TRACES_EXPORTER` | `none` | OTLP trace exporter (`otlp` or `none`)
| `OTEL_EXPORTER_OTLP_ENDPOINT` | `http://localhost:4317` | OTLP collector gRPC endpoint
|===

== Health Endpoints

|===
| Path | Description

| `GET /healthz` | Liveness — returns 200 if the process is up
| `GET /readyz` | Readiness — returns 200 if a `SELECT 1` against the database succeeds
|===

Use `/readyz` as the Kubernetes readiness probe and `/healthz` as the liveness probe. A failing `/readyz` indicates a lost database connection.

== Startup Dependencies

[source,yaml]
----
depends_on:
  pg-seed:    # seed data inserted after all Liquibase migrations complete
    condition: service_completed_successfully
  keycloak:   # JWT verification endpoint must be reachable
    condition: service_started
----

Note: `liquibase-treatments` runs independently before `pg-seed`. If it fails, `pg-seed` will not run and `treatments-backend` will start against an empty or partially migrated schema.

== Database

Schema is managed exclusively by the `liquibase-treatments` container (Liquibase migrations in `src/main/resources/db/changelog/`). The application role is DML-only.

=== Schema

* `treatments` — stores all treatment events

|===
| Column | Type | Notes

| `id` | UUID PK | Generated by the service
| `user_id` | UUID | References Keycloak user (no FK)
| `type` | TEXT | `BOLUS`, `BASAL`, `CARBS`, `CORRECTION_BOLUS`, `COMBO_BOLUS`, `TEMP_BASAL`, `EXERCISE`, `NOTE`, `BG_CHECK`, `PUMP_SUSPEND`, `SITE_CHANGE`, `SENSOR_INSERT`, `INSULIN_CHANGE`
| `data` | JSONB | Treatment payload; structure follows Nightscout conventions per type
| `treated_at` | TIMESTAMPTZ | When the treatment was administered
| `created_at` | TIMESTAMPTZ | Insertion timestamp
| `status` | TEXT | `ACTIVE` or `ARCHIVED`
| `notes` | TEXT | Optional free-text note (nullable)
|===

=== Data Retention

Treatment records are never physically deleted. All deletion is soft: `status` is set to `ARCHIVED`. Archived records are excluded from default read queries. The EU MDR requirement is 7-year retention — do not purge rows.

=== Delete Access Restriction

The `DELETE /api/v1/users/{userId}/treatments/{id}` endpoint archives a treatment record. This endpoint is restricted to `DOCTOR` and `ADMIN` roles. Patients may not delete their own treatment records — they can only archive. This restriction is enforced at the route level in `TreatmentRoutes.kt`.

== Scaling

`kdiab-treatments` is **stateless at the application layer** — all state is in PostgreSQL. It can be scaled horizontally. Coordinate `DB_POOL_SIZE` with the PostgreSQL `max_connections` setting when running multiple instances.

Resource limits per instance (from `docker-compose.yml`): 512 MB RAM, 1 CPU.

== Structured Logging

All logs are emitted as JSON to stdout. Key fields:

* `level`, `timestamp`, `message`
* `Correlation-ID` — from `X-Correlation-ID` header or generated on ingress
* `userId` — present in service-layer log entries

== Common Operations

=== List a patient's recent treatments

[source,bash]
----
curl -s http://localhost:8083/api/v1/users/$USER_ID/treatments \
  -H "Authorization: Bearer $TOKEN" \
  -G -d "page=0" -d "size=20" | jq .
----

=== Archive a treatment (doctor or admin only)

[source,bash]
----
curl -X DELETE http://localhost:8083/api/v1/users/$USER_ID/treatments/$TREATMENT_ID \
  -H "Authorization: Bearer $DOCTOR_OR_ADMIN_TOKEN"
----

Returns `204 No Content`. The record is soft-deleted (status → `ARCHIVED`).

=== Verify a patient token can read but not delete

[source,bash]
----
# Should succeed (200)
curl http://localhost:8083/api/v1/users/$USER_ID/treatments \
  -H "Authorization: Bearer $PATIENT_TOKEN"

# Should return 403 Forbidden
curl -X DELETE http://localhost:8083/api/v1/users/$USER_ID/treatments/$ID \
  -H "Authorization: Bearer $PATIENT_TOKEN"
----

== Troubleshooting

=== 403 on DELETE when using a doctor token

Confirm the doctor's JWT includes the `DOCTOR` role in the `roles` claim. If the doctor recently had their role assigned, they must re-login to get a new token containing the updated role.

=== Readiness check fails (`/readyz` returns 500)

1. Confirm `JDBC_URL`, `DB_USER`, `DB_PASSWORD` are set correctly.
2. Verify the `kdiab-treatments` PostgreSQL database exists and the application user has DML privileges.
3. Check PostgreSQL is accepting connections: `psql $JDBC_URL -U $DB_USER -c "SELECT 1"`.

=== Liquibase migration conflict

If `liquibase-treatments` exits non-zero, the `DATABASECHANGELOGLOCK` table may need clearing:

[source,sql]
----
DELETE FROM DATABASECHANGELOGLOCK;
----

Then re-run the `liquibase-treatments` container before starting `treatments-backend`.
