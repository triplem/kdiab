== Overview

This document is the authoritative developer reference for all clinical formulas, threshold
definitions, endpoint contracts, and data-flow details for the kdiab-analyze PDF patient
report feature (epic #1117).

The report aggregates data from `kdiab-measures` (CGM/BGM readings) and `kdiab-profiles`
(active insulin profile) via six dedicated endpoints, all implemented in `AnalyticsService`
under `kdiab-analyze`.

See ADR-ANA-019 for the architectural rationale behind server-side computation and browser-based
PDF export.

== Clinical Formulas

All metrics are computed from CGM readings filtered to the requested date range.
When the user's JWT contains `glucose_unit = mmol/L`, values are converted to mg/dL
(`mmol/L × 18.0182`) before any formula is applied.
The response returns values in the user's display unit.

=== Formula Table

[cols="1,2,3,2"]
|===
|Metric |Formula |Notes |Source

|eHbA1c
|`(mean_glucose_mg_dL + 46.7) / 28.7`
|Returns `null` if no CGM readings in range.
Per-day eHbA1c computed from same formula applied to daily mean.
|Nathan et al. 2008 (ADAG study)

|GVI (Glucose Variability Index)
|`SD(glucose_mg_dL) / mean(glucose_mg_dL)`
|Returns `null` if fewer than 2 readings.
Lower is better; values > 0.36 indicate high variability.
|Peyser et al. 2011

|PGS (Personal Glycaemic Score)
|`GVI × mean_glucose_mg_dL × (1 + (% > 140 mg/dL / 100))`
|Full Rodbard 2011 formula; returns `null` if no data.
Scale: ≤ 35 optimal, 35–100 adequate, > 100 suboptimal.
|Rodbard 2011

|GRI (Glucose Risk Index)
|`3.0 × (%<54) + 2.4 × (%54–70) + 1.6 × (%180–250) + 0.8 × (%>250)`
|Input percentages are values in [0, 100].
Scale: 0 = no risk, 100 = maximum risk.
|Klonoff et al. 2023

|CGP axes (Continuous Glucose Profile)
a|Five axes, each normalised 0–100 relative to reference population:

* **ToR** — Time-on-Range percentage
* **VarK** — Coefficient of variation (`SD / mean × 100`)
* **Hypo intensity** — Weighted hypo burden: `sum(max(0, 80 - sgv) × dt_min)`
* **Hyper intensity** — Weighted hyper burden: `sum(max(0, sgv - 140) × dt_min)`
* **Mean glucose** — mean CGM in display unit
|Each axis normalised to reference range defined in Vigersky 2018 Table 1.
|Vigersky and Sherr 2018

|PGR (Percentage-of-Glucose-at-Range)
|`100 × (A1 × A2 × A3 × A4 × A5)^(1/5)`
|Geometric mean of the five normalised CGP axis scores.
100 = perfect reference; < 70 requires discussion with care team.
|Vigersky and Sherr 2018

|AGP percentiles
|Sort-based linear interpolation per 5-min bucket.
`p(k) = sorted[floor((n-1)×k)] + frac((n-1)×k) × (sorted[ceil((n-1)×k)] - sorted[floor((n-1)×k)])`
|288 buckets (0–287), each covering one 5-min interval of the 24-hour day.
Buckets with no readings return `null` percentile values.
|Standard percentile interpolation

|Histogram bins
|Frequency count per 5 mg/dL bin from 40 to 400 mg/dL (72 bins).
For mmol/L users the response bins are rounded to 0.3 mmol/L.
|Bin index `i = floor((sgv_mg_dL - 40) / 5)`.
Readings outside [40, 400] are clamped to the nearest bin.
|—
|===

== TIR Zone Thresholds

Five-zone model per ATTD/AGC consensus (Battelino et al. 2019).

[cols="1,1,1,2"]
|===
|Zone |mg/dL range |mmol/L range |Display colour (CSS)

|Very Low
|< 54
|< 3.0
|`#7b2d2d` (dark red)

|Low
|54 – 70
|3.0 – 3.9
|`#e74c3c` (red)

|In Range
|70 – 180 (standard) +
or `Profile.analysisLow` – `Profile.analysisHigh` (custom)
|3.9 – 10.0 (standard)
|`#27ae60` (green)

|High
|180 – 250
|10.0 – 13.9
|`#f39c12` (yellow/amber)

|Very High
|> 250
|> 13.9
|`#e67e22` (orange)
|===

NOTE: The standard 70–180 mg/dL In Range boundary is used for GRI, PGS, and all report summary
statistics.  The custom `Profile.analysisLow` / `Profile.analysisHigh` boundary is used only for
the TIR bar displayed on the summary page and the colour overlay on the AGP chart (where a
non-default target range has been configured by the clinical team).

== Threshold Sources

Which source defines each threshold is clinically significant.  This table is the canonical
mapping; do not use `UserSettings` alarm fields for report computations.

[cols="1,2,2"]
|===
|Usage |Source field |Notes

|**TIR (report summary / AGP overlay)**
|`Profile.analysisLow`, `Profile.analysisHigh`
|Defaults to 70 / 180 mg/dL when the profile fields are absent.
Set by clinical team together with patient; not a user-editable alarm.

|**Target zone line on charts** (AGP, Tagesgrafik, Wochengrafik)
|`Profile.targets: List<TargetSegment>`
|Time-of-day segmented target range.
Rendered as a shaded band on all glucose-over-time charts.

|**Alarm / alert thresholds** (CGM alarm notification)
|`UserSettings.hypoAlarmThreshold`, `UserSettings.hyperAlarmThreshold`
|Used exclusively for alert notifications.
*Must not* be used for report computations or chart overlays.

|**eHbA1c / GVI / PGS / GRI**
|Fixed mg/dL constants per formula specification
|See Formula Table above.

|===

== Patient Display Name

The patient's full name is rendered on the report cover page.
The name is sourced from standard OpenID Connect claims in the Keycloak-issued JWT:

* `given_name` — first name
* `family_name` — surname

These claims are mapped by Keycloak's built-in OIDC profile claim mapper and extracted in
`kdiab-common/plugins/Security.kt` when building `UserPrincipal`.
No separate name lookup call to `kdiab-users` is required.

The display name is formatted as `{given_name} {family_name}` in the frontend.
If either claim is absent the available claim is used alone; if both are absent the report
renders the `userId` UUID instead.

== Report API Endpoints

All endpoints share the following common contract:

[cols="1,3"]
|===
|Auth |Bearer JWT (same token forwarded to upstream services)
|Path prefix |`/api/v1/users/{userId}/analytics/`
|Access control |`UserPrincipal.canAccess(userId)` — self, admin, or doctor with assigned patient
|Max date range |365 days (`to - from ≤ P365D`); requests exceeding this return `400 Bad Request`
|Short-period warning |Response includes `"warningShortPeriod": true` when `to - from < P14D`
|===

The profile endpoint (`/profiles/active`) is consumed separately by the frontend to render:

* The Profil report page (ICR, ISF, targets, basal segments)
* The Basalrate chart
* The `Profile.analysisLow` / `Profile.analysisHigh` TIR overlay

All six metric endpoints consume only `kdiab-measures` (CGM data).
No treatment data is fetched for the current report pages.

== Basal Rate Computation Algorithm

The Basalrate report page renders the scheduled basal rate at each hour of the day from the
active profile.

A profile contains a list of `BasalSegment` objects, each with:

* `startTime: LocalTime` — when this rate becomes effective (24-hour, e.g. `06:00`)
* `rate: Double` — basal rate in U/h for this segment

The algorithm to find the effective rate at a given `targetHour` (0–23):

. Sort segments ascending by `startTime`.
. Iterate through segments.
. The effective segment for `targetHour` is the *last segment* whose `startTime.hour ≤ targetHour`.
. If no segment satisfies the condition (all segment start times are after `targetHour`), wrap
  around and use the *last segment in the list* (the overnight segment that started before midnight
  and is still active at hour 0–N).

This mirrors the basal-calculation logic in `reconstructBasalBlocks()` used by the dashboard CGM chart.

[source,kotlin]
----
fun effectiveRateAtHour(segments: List<BasalSegment>, targetHour: Int): Double {
    val sorted = segments.sortedBy { it.startTime }
    return sorted.lastOrNull { it.startTime.hour <= targetHour }?.rate
        ?: sorted.last().rate  // wrap-around: overnight segment still active
}
----

The Basalrate chart renders 24 bars (one per hour) using this function for hours 0–23.
