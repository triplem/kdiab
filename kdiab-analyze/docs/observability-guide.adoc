= Local OpenTelemetry Observability Stack
:toc: left
:icons: font
:source-highlighter: rouge

== Overview

kdiab ships an opt-in OpenTelemetry observability overlay for local development.
By default the stack starts without any observability infrastructure — all eight backends have
`OTEL_TRACES_EXPORTER=none` so the SDK never opens a connection.
Passing `-o` to `podman-up.sh` activates the overlay, which adds an otel-collector, Jaeger,
Prometheus, and Grafana alongside the main stack.
No changes to the base `docker-compose.yml` are required.

== Architecture

----
kdiab backends (8 services)
  └─► OTLP HTTP :4318 ──► otel-collector
                               ├─► otlp/jaeger → Jaeger :4317   (traces)
                               └─► prometheus   → :8889          (metrics exposition)
                                                     └─► Prometheus :9090
                                                               └─► Grafana :3010
----

All backends push both traces and metrics via OTLP to the collector.
The collector fans out: traces go to Jaeger via OTLP; metrics are converted to Prometheus exposition format and scraped by Prometheus.
Grafana unifies both data sources and provides a single dashboard UI.

== Quick Start

[source,bash]
----
# Start the full stack including observability services
./podman-up.sh -o --build

# In another terminal — make a request to any backend
curl -s http://localhost:8080/api/v1/health

# Open Jaeger UI and find the trace
# http://localhost:16686 → select service "kdiab-measures" → Find Traces
----

== How Tracing Works

Each backend has the following environment variables set by the root `docker-compose.yml`:

[source,yaml]
----
OTEL_SERVICE_NAME: kdiab-<service>
OTEL_TRACES_EXPORTER: ${OTEL_TRACES_EXPORTER:-none}
OTEL_EXPORTER_OTLP_ENDPOINT: ${OTEL_EXPORTER_OTLP_ENDPOINT:-http://localhost:4318}
----

When `./podman-up.sh -o` is used, the script exports:

[source,bash]
----
export OTEL_TRACES_EXPORTER=otlp
export OTEL_EXPORTER_OTLP_ENDPOINT=http://otel-collector:4318
----

These values are picked up by the compose file, overriding the `none` defaults.
Each HTTP request also carries an `X-Correlation-ID` header (generated by the frontend's
Axios interceptor or by the backend `CallId` plugin) which appears as a span attribute in Jaeger,
allowing a single frontend request to be correlated with spans across multiple services.

== How Metrics Work

The collector exposes a Prometheus exposition endpoint on `:8889`.
Prometheus scrapes it every 15 seconds (`config/otel/prometheus.yml`).
All kdiab backends push metrics via OTLP (same endpoint as traces) — no per-service scrape
configuration is needed.

The pre-provisioned Grafana dashboard **kdiab — Ktor / JVM Overview** shows:

* HTTP request rate per service (req/s)
* HTTP p99 latency per service (ms)
* JVM heap used and committed (MB)
* HikariCP active DB connections per service

To view it: **Dashboards → kdiab — Ktor / JVM Overview**.

The Jaeger datasource is also pre-provisioned in Grafana.
Open **Explore → Jaeger** to search traces directly from Grafana, or click a trace link in the dashboard.

== Running Without Observability

Omitting `-o` is always safe.
The eight backends default to `OTEL_TRACES_EXPORTER=none`, which means the OpenTelemetry SDK never
attempts to open a connection to the collector.
No OTLP connection errors will appear in service logs when the observability overlay is not running.

[source,bash]
----
# Default — no observability services started, no errors
./podman-up.sh --build
----

== Teardown

[source,bash]
----
# Stop containers (data volumes preserved)
./podman-clean.sh -o

# Stop containers and wipe prometheus_data + grafana_data volumes
./podman-clean.sh -o -v
----

WARNING: `-v` also removes `postgres_data`. Use it only when a full reset is intended.

== Troubleshooting

=== No traces appear in Jaeger

. Check that `OTEL_EXPORTER_OTLP_ENDPOINT` is set to `http://otel-collector:4318` in the backend's
  container environment:
+
[source,bash]
----
podman inspect kdiab-measures | grep OTEL
----
. Verify the collector is healthy:
+
[source,bash]
----
podman logs kdiab-otel-collector
----
. Confirm the otel-collector container is running: `podman ps | grep otel`.

=== Prometheus target shows as DOWN

The collector's Prometheus exporter listens on `:8889`.
Check collector logs for startup errors:

[source,bash]
----
podman logs kdiab-otel-collector | grep -i "prometheus\|8889"
----

=== Grafana dashboard shows no data

The metrics pipeline in the collector must be receiving OTLP metrics from backends.
Check the collector pipeline:

[source,bash]
----
podman logs kdiab-otel-collector | grep -i "metric\|pipeline"
----

If no metrics are flowing, confirm `OTEL_METRICS_EXPORTER=otlp` is set in the backend environment
(it is set automatically when `-o` is passed to `podman-up.sh`).
